# 投稿・画像の共通WALと画像の重複排除

Aの永続化済み画像の再利用をBの共通WALへ組み込み、実装・デプロイ済み。
3号機のGoアプリを更新し、公式初期化で競技データを作り直した。
負荷時の得点・性能は未測定。ベンチマーカーは実行していない。

## 変更した動作

投稿イベントと画像本体を、事前確保済みの512MiBのWALへ記録する。
到着済みレコードを単一の同期workerがfdatasyncし、捕捉した境界までを公開する。
同期中の後着レコードは次の同期で確定する。固定の収集待ちは追加しない。

画像はSHA256で識別し、保存中の同一画像は完了通知を共有する。
永続化済みなら追加の書込み・同期なしで再利用する。
同じ画像の再アップロードでも、icons行の作成とAPIのID発行は維持する。

画像本体はJSON/base64へ変換せず、WALのメタデータに続くバイナリとして保存する。
最大64KiBの断片に分け、writerは画像ジョブを巡回しながら到着済みの投稿も取り込む。
画像の最後の断片が同期できてからDBのハッシュを更新し、commit後に公開・通知する。
個別画像ファイルの作成、rename、ファイル・ディレクトリ同期は負荷経路から除去した。

GETは永続化済みの断片位置を使ってWALから読み、画像本体を常駐させない。
1・2号機のicon readerとnginxへの通知・転送仕様は維持する。
画像・icon_hash・ETagの一致と、更新後2秒以内の反映も維持する。

## 復旧・初期化・上限

WAL形式はISUPWAL4。CRC、連番、完了フッターを検査して投稿と画像索引を復元する。
画像全体のSHA256も検証する。未完了画像は読取り索引に含めず、再保存できる。
DBが参照する画像が欠ける場合は起動失敗にする。

初期化は受付を止めて旧writerを閉じ、公式SQL・DNS初期化を行って新世代を作る。
fallback画像を共通WALへ永続化し、画像・参照索引を揃えてから受付を開始する。
旧WAL世代は初期化後に削除する。旧形式との互換運用・切替フラグは追加していない。

画像索引は最大32,768ハッシュ、保存中の画像本体は合計16MiB、画像単体は最大10MiB。
WALの未同期部分は既存の16MiB上限を維持する。
受付・容量の上限を超えた画像を成功扱いしたり、既存データを捨てたりしない。
再起動後に未完了画像を再保存する際は、同じハッシュの古い未完了エントリを置き換える。

事前の読み取り確認では、3号機の画像は191ファイル・約13MB、
投稿WAL使用量は約13.4MB、ディスク空きは約31.3GBだった。
現行の512MiB容量を維持した。これは負荷上限の実証ではなく、現行データ量に基づく判断。

## 計測と比較

追加したsnapshot metricsは次の4項目。既存collectorが取り込むため基盤の変更は不要。

- icon_reuses_total: 保存中・永続化済み画像の再利用要求数。
- icon_uploads_total: 新たに永続化を完了した画像数。fallbackも含む。
- icon_wal_bytes_total: 新たに同期済みとなった画像本体のバイト数。
- icon_wal_chunks_total: 新たに同期済みとなった画像断片数。

wal_records_totalは投稿イベントだけを数える。
wal_syncs_totalとwal_sync_ns_totalは画像を含む共通WALの同期回数・時間。
durable_seqとpublished_seqは投稿・画像断片を合わせた連番。
同期効率を比較するときは、投稿数と画像断片数を分けて扱う。
プロセス再起動でカウンターはリセットされるが、WALの世代・位置・データは維持する。

基準RUNは20261002-024920、522,793点、PASS、必須成果物の内容検査も成功。
同RUNの59.001秒のカウンター差分は、73,657投稿イベント、45,930同期、
同期時間44.738秒、単独レコード同期28,845回。
実負荷60.001秒ではコメントPOSTが33,635件、平均2.977ms、p99 7msだった。

過去の500µs収集待ちは、59秒の同期時間を8.108秒削減した一方、
10.875秒の追加待ちを生み、投稿処理量を伸ばせなかったため再導入しない。
画像の重複同期を除き、投稿と画像の同期を共有することでI/O競合の削減を狙う。
投稿が増えれば同期回数も増え得るので、回数だけでは採用を判断しない。

次RUNは同じ負荷窓で、得点、コメントPOSTの件数・平均・p99、
WAL同期時間/投稿イベント、画像の新規保存・再利用数、3号機のI/O待ちを比較する。
得点への寄与と負荷中の同期待ち短縮は未確定。

## 操作経路

- task inspect-shared-wal: ホスト・容量・計測停止・WAL状態の読取り確認。
- task deploy-shared-wal-dry: 共通WAL導入時の配布・初期化の対象と順序。
- task deploy-shared-wal: 形式変更を伴う配布と競技データの公式初期化。
- task deploy-app: 導入後の通常の配布・再起動。保存済みWALを復元する。

競技固有のタスク・配布手順はTaskfile.contest.ymlとtools/contest/deployments.yamlに置いた。
