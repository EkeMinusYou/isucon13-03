# DNS登録の非同期同期とWAL同期間隔の変更

2026-10-09。ユーザーの指示により1号機のDNSと3号機のGoアプリへ反映する。
永続性の要件は通常のサービス停止・再起動とOS再起動。電源断・強制リセットは対象外。

## 変更

- DNS登録は完全なジャーナルレコードを追記し、名前とserialを公開してから応答する。
  キュー投入だけでは成功にしない。DNS問い合わせは追記済みの名前を直ちに返せる。
- ファイル同期は独立workerが100msごと、または未同期量64KiB以上で実行する。
  同期中も追加登録と検索は継続できる。要求や名前の複製を同期完了まで保持しない。
- statusにpublished_seq、synced_seq、pending_bytesを追加する。
  同期対象の連番を捕捉し、同期中に公開された追加登録は次の同期へ含める。
- 初期化は進行中の同期を待ってからファイルと世代を置き換える。
  通常停止は受付を閉じ、受理済みの追記を排出し、残りを同期してからファイルを閉じる。
- 書込み失敗は登録を失敗にする。同期失敗は以後の登録・検索を停止し、statusをfailedにする。
- 投稿・画像WALの同期timerを10msから100msへ延長する。
  1MiBでの同期通知、未同期量16MiB、全容量512MiBと公開手順は維持する。

DNS登録の応答から同期待ちを除き、同期回数の削減を狙う。
投稿・画像の同期は既に応答経路から分離されているため、こちらは背景I/O削減が目的。
今回の得点への効果は未測定。ベンチマーカーは実行しない。

## 確認

- task check-fast-paths: 全Goアプリのrace検証。DNS同期停止中の応答・検索、
  同期失敗、初期化との排他、通常終了後の復元、投稿・画像の既存検証が成功。
- task check-dns-linux: 実ホストのLinux/amd64でDNS検証が成功。
  子プロセスの復元検証は正常終了・close時の同期に変更した。
- 登録smokeは最初のHTTP入口で登録し、後の入口でログイン・DNS・HTTPSを読む。
  同じユーザーを入口ごとに重複登録しない。

## 配布・再起動結果

- 3台のLinux/amd64と計測停止を確認し、ローカルでクロスコンパイルした。
  task deploy-dns-dry / deploy-app-dryで配布先と再起動対象を確認し、
  task deploy-dns / deploy-appで1号機のDNSと3号機のアプリへ反映した。
- task check-dns / check-app-deploymentで役割と稼働バイナリの一致を確認した。
  SHA256: 507713b35bb223203b14378141d3e27f932f6cef04cd10561f74fa8003d4a046。
- 配布時にDNSの既存世代・serial・登録件数・ログ量を維持した。
  画像更新と新規登録のAPI確認、投稿・モデレーション等のWAL書込み確認が成功した。
- DNSとアプリを同じTaskfile経路で通常再起動し、両HTTP入口で画像・投稿・ユーザーを
  取得できた。新規ユーザーのログイン、DNS検索、サブドメインHTTPSも成功した。
- DNS再起動前後でepoch=3192342187353351818、serial=1791501911、dynamic_names=4010、
  entries=5288、log_bytes=1154912が一致した。
- 投稿・画像WAL再起動前後で世代6dfaccc3-e5b2-4a27-9f51-90baff48c84d、
  durable_seq=published_seq=81035、使用量27,959,918 bytes、rows=91117が一致した。
  pending_bytes=0、failed=false。

ログは.task/dns-async-*に保存した。ベンチマーカーは実行していない。
今回のsmokeと再起動確認は正当性の検証であり、性能改善量の測定ではない。
