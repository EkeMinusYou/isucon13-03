# 事前確保したWALとデータ同期

2026-10-01。WAL同期の軽量化について、ユーザーの実装・デプロイ指示に基づく変更。

## 変更

3号機のGoアプリは、公式初期化時に世代ごとの512MiBのWALをゼロで実書込みし、ファイルと親ディレクトリを同期してからDBの世代を公開する。
負荷中は固定サイズのファイル内へ書き込む。Linuxでは投稿の同期を`fdatasync`で行い、同期開始前に取り出した完全フレームまでだけ成功応答・メモリ公開を許す。
追記と同期の並行化、配信ごとの順序、DB projector、NG判定は既存の仕組みを使う。

新形式`ISUPWAL2`の世代ヘッダはUUIDと物理容量を持つ。各フレームはJSON payloadの長さ・CRC、長さの補数・ヘッダCRC、payload、ヘッダを複製した完了印から成る。
常にフレームヘッダ1個分の未使用領域を残し、容量超過の投稿を成功扱いしない。WALの512MiB上限とDB未反映量の16MiB上限を維持する。

## 復元

- 物理サイズと世代ヘッダの容量が一致することを確認する。
- 未使用のゼロヘッダから先がすべてゼロであることを検査する。
- 完了印の欠けた末尾だけをゼロへ戻す。欠けたヘッダは、その後がすべてゼロの場合だけ消せる。ファイルを切り詰めず、事前確保を維持する。
- 完了したフレームのCRC・連番の不整合、未使用領域や不完全フレームの後にある非ゼロデータ、DB反映位置を失う末尾、物理ファイルの切詰めを拒否する。
- 同期済みでDB未反映の完全フレームは再生し、反映済み投稿と削除済み投稿を再INSERTしない。

初期化・再起動時に未使用領域を読み取って検査するため、最大512MiBの読取りが増える。初期化の実書込み・同期・検査を含め、公式の42秒以内を確認する。

## 確認

`task check-fast-paths`のrace付きテストが成功。
`task check-app-improvements`により、2号機の一時DBとLinux/amd64のテストバイナリで永続化・末尾復元・破損拒否・採番・投稿とNG処理・DB反映の原子性を確認した。
テスト用WALは1MiBとし、本番と同じ形式・同期・復元処理を通す。本番の512MiB確保は正式初期化で確認する。

## デプロイ結果

全ホストのLinux/amd64と計測停止を確認し、`task build`でローカルクロスコンパイルした。
既存の`task deploy-wal-posts`を実行し、`task db-recreate`による競技DB再作成・公式初期化、公開APIの投稿と読取り、3号機Goの再配布・再起動後の読取りを完了した。
この既存経路には2号機MySQL・アイコンサービスと1号機DNSの再起動も含まれる。

- 512MiBの作成と検査を含む公式初期化は11.536秒で成功（SSHを含むactivationの所要時間、curlの上限42秒）。
- 公開nginx経由の認証APIとコメント・リアクションの書込み・読取り、再起動後の同じ投稿の取得が成功。
- 再起動前後でWAL世代を維持し、`durable_seq=applied_seq=2`、`pending_bytes=0`、`failed=false`。DBの反映位置も2。
- 再起動前後のデータ集計が一致（livecomments=1002、reactions=1002、total_tip=7）。
- 本番WALの物理サイズとヘッダ容量はともに536,870,912 bytes。割当て済みブロックは1,048,584個（512 bytes単位）。`filefrag`で2 extentsを確認し、未書込み領域を示す`unwritten`フラグはない。
- 実行中のGoバイナリがローカルのビルド結果と一致し、ホストごとのサービス配置・DB接続・DNS応答の確認が成功。

検証ログは`.task/preallocated-wal-mysql.log`、デプロイログは`.task/preallocated-wal-deploy.log`。ベンチマーカーは実行していない。
