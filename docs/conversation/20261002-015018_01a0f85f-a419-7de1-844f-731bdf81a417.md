1. **狙いと初期値**

基準RUNでは67,610イベントに対して41,731回同期し、平均1.62件／回でした。1回の同期は平均1.05msです。すでに追記と同期は並行化されているため、次の改善対象は**1回の同期に含めるイベント数**です。

| 項目 | 設計値 |
|---|---|
| 即同期する件数 | 未同期イベントが4件以上 |
| 収集期限 | 最古の未同期フレームの追記完了から500µs |
| 期限を過ぎた未同期フレーム | 追加待ちなしで同期 |
| 同期対象 | 取り出した時点の未同期フレームすべて |
| 件数の数え方 | コメント・リアクション・NG登録などを合算 |

4件は開始条件であり、同期対象の上限ではありません。すでに10件あれば10件をまとめます。現在のフレーム上限64件と、受付上限256件を維持します。

500µsは検証する初期値です。低負荷時には遅延が増え、タイマーの起床も遅れる可能性があるため、性能向上はまだ確定していません。

2. **保持する状態と処理**

[postStore](/Users/mineo/src/github.com/EkeMinusYou/isucon13-03/webapp/go/post_store.go:41)に、`walMu`で保護する状態を2つ追加します。

| 状態 | 内容 |
|---|---|
| `pendingRecords` | 未同期フレームに含まれるイベント総数 |
| `pendingSince` | 最古の未同期フレームの追記完了時刻 |

追記workerは、完全なフレームを書き終えた後、既存の`pending`へ追加します。空だった場合だけ`pendingSince`を設定し、件数を加算して既存の`syncWake`へ通知します。

同期workerは次の条件を確認します。

```text
未同期フレームなし
  → 通知を待つ

終了処理中
  → 残りを直ちに同期する

pendingRecords >= 4
または now >= pendingSince + 500µs
  → 未同期フレームをすべて取り出して同期する

それ以外
  → 新しい追記通知、または収集期限を待つ
```

**追記通知を受けても期限を延長しません。** タイマーはworker内で1個を再利用し、空の状態では停止します。通知は再確認のきっかけとして扱い、同期条件の確認と対象の取り出しは同じ`walMu`の区間で行います。待機・`fdatasync`・メモリ反映中はこのロックを保持しません。

前回の同期中に蓄積したフレームにも同じ期限を適用します。すでに500µs経過していれば、次の同期へ直ちに進みます。

3. **正当性を維持する条件**

[現在の同期処理](/Users/mineo/src/github.com/EkeMinusYou/isucon13-03/webapp/go/post_wal.go:490)の、次の順序を維持します。

```text
完全フレームを書き込む
→ 同期対象の末尾境界を捕捉する
→ fdatasyncが成功する
→ 捕捉したイベントをWAL順にメモリへ反映する
→ 各要求の完了を通知する
→ HTTP成功応答
```

- 同期開始後に追記されたフレームは、次回の同期対象とします。
- 配信ごとの`gate`は完了通知まで保持し、NG登録・投稿・削除の順序を維持します。
- 受付済み要求は、クライアントがキャンセルしても永続化・公開まで処理します。
- 同期失敗時は成功通知を返さず、既存のエラー状態へ移ります。
- 追記worker終了後は収集待ちを解除し、残ったフレームを処理してから終了します。

WAL形式・採番・CRC・末尾復旧は既存処理を使います。今回追加する待ちは揮発状態なので、再起動時の再生処理に追加情報は不要です。公式のNG判定や統計・課金の意味も維持します。
