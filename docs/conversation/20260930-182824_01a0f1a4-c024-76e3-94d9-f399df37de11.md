**② writerの変更**

[mutationRequest](/Users/mineo/src/github.com/EkeMinusYou/isucon13-03/webapp/go/mutations.go:19)の任意の関数を、コメント・リアクション・NG登録・通報・入退室の型付き操作へ置き換えます。

初回実装では、現在の**4並列・最大32件・収集待ち1ms・READ COMMITTED**を維持します。並列数や待ち時間を同時に変えず、一括化の効果を比較できます。

処理は次の流れです。

```text
入力・参照情報の確認
    ↓
配信IDで既存の4キューへ投入
    ↓
操作を区間に分ける
    ↓
区間内のNG判定・INSERTを一括実行
    ↓
COMMIT
    ↓
採番結果を応答へ反映して返す
```

**一括化の区切り**

| 操作 | 処理方法 |
|---|---|
| コメント | NG判定を1つのSELECTへまとめ、通過した投稿を複数行INSERT |
| リアクション | 複数行INSERT |
| NG登録・通報・入退室 | 前の投稿を実行してから、その操作をキュー順に実行 |

コメントとリアクションは、区間内でそれぞれの受付順を保ってまとめます。NG登録や通報を越える並べ替えはしません。

例えば、`投稿A → NG登録 → 投稿B`なら、Aを保存し、NG登録と削除を実行してからBを判定します。`投稿A → 通報 → NG削除`でも、通報がAの本文を保存する順序を維持します。

**NG判定と採番**

NG判定は、現在の`EXISTS`をリクエスト番号付きの`UNION ALL`でまとめます。判定はMySQLで行い、`utf8mb4_general_ci`、`%`・`_`・エスケープの意味を維持します。

IDはMySQLのAUTO_INCREMENTを使います。実機は採番間隔1、対象テーブルのトリガーなしでした。全行を自動採番する通常の複数行`INSERT ... VALUES`に限定し、`LastInsertId()`と行位置から各投稿のIDを対応付けます。[MySQLの採番仕様](https://dev.mysql.com/doc/refman/8.0/en/innodb-auto-increment-handling.html)

応答に必要なユーザー・配信・タグの参照は書込み前に確認します。COMMIT後に参照失敗が判明する構造を避け、応答の組み立てはwriterの外へ移します。アイコンhashは応答時に既存の更新情報を参照します。

**失敗の扱い**

- NGに該当した投稿はその1件を400とし、他の投稿を続行。
- SAVEPOINTは各一括INSERTと、区切りとなる操作に置く。
- 文字数超過などのデータエラーでは、その一括INSERTを戻して分割し、不正な1件を特定。他の正常な投稿は保存。
- デッドロック・接続断・期限超過・COMMIT失敗はトランザクション全体を失敗とし、成功応答を返さない。
- クライアント切断後も、実行開始済みの操作はworkerの独立した期限で処理。他の投稿を巻き込まない。

デッドロックはトランザクション全体が取り消されるため、データエラーのSAVEPOINT処理と分けます。[MySQLのエラー処理](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html)

**削減できる仕事と評価条件**

正常なコメント8件をまとめられた場合、BEGIN・COMMITを除いたDB往復は、現行の**24回から3回**になります。リアクション8件なら**16回から2回**です。実際の削減量は、集まる件数とNG登録などの区切りの頻度で変わります。

- 4並列でのIDと応答本文の対応
- 投稿・NG登録・通報・削除の順序
- 不正な1件の分離、COMMIT失敗、切断、停止時のキュー消化
- NG判定の既存テストと再起動後の取得
