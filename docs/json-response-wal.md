# JSON応答の再利用とWAL同期待ちの削減

2026-10-02。ユーザーの実装・デプロイ指示に基づく変更。対象は3号機のGoアプリ。
比較基準は20261002-020536、479344点、PASS。ベンチマーカーは実行しない。

## 根拠

負荷中の59秒で67545イベント、33914同期、同期時間35.729秒、収集待ち10.875秒。
収集待ち追加前の20261002-013620は67610イベント、41731同期、同期時間43.837秒。
同期時間の削減8.108秒より追加待ちが長く、同期と収集待ちの合計は2.767秒増えた。

最新RUNの180秒のCPUプロファイルでは、全体68.26 CPU秒のうちJSON出力経路が15.38秒。
コメント一覧、リアクション一覧、配信検索のc.JSON経路が主な消費箇所だった。
CPU・goroutineの累計待ち・負荷中のカウンタ差分は異なる単位と窓であり、合算しない。

## 変更と正当性

- UserとLivestreamのJSONを参照ごとに1版保持し、コメント一覧・リアクション一覧・
  配信検索で再利用する。アイコンハッシュとタグカタログを版の条件にする。
- 新規参照のcommit/publicationを待ってからキャッシュへアクセスする。要求内では
  ユーザーの同じ版を使い、投稿者と配信者が同一の場合もハッシュを揃える。
- キャッシュ済みJSONは不変とし、出力バッファへコピーする。一覧の行の選択、limit、
  順序、タグの重複、モデレーションによる削除は現行の処理に従う。
- 文字列は標準JSONでエスケープし、空配列、整数、改行、pretty出力、Content-Typeを維持する。
- 出力バッファを再利用し、128KiBより大きいバッファはpoolへ戻さない。
- WALの500µs収集待ちと4件の同期開始条件、不要なタイマー・待ちカウンタを削除する。
  到着済みの完全フレームを直ちに取り出し、同期中の追記は次のグループへまとめる。
- fdatasync成功後の公開・応答、捕捉したフレーム境界、配信ごとの順序、終了時の排出、
  ISUPWAL3の形式と復旧処理を維持する。DB再作成や公式初期化は不要。

追加費用は共有JSONのメモリ、版の確認、更新後のJSON生成、応答へのバイト列コピー。
応答の転送量は減らない。WALの同期回数は増える可能性があり、得点改善幅は未確定。

## 確認と評価

task check-fast-pathsで、標準JSONとの一致、特殊文字・大きな整数・空配列、
アイコンとタグの更新、commit待ち、同時読取りのrace、WAL同期境界と排出を確認する。
task check-app-improvementsで、一時DBを使ってAPIのlimit・順序・タグ重複、
アイコン更新、モデレーション、全イベントの再起動後の復元を確認する。

正規のtask deploy-appで3号機へ配布・再起動し、公開APIとWAL状態を確認する。
次のユーザー実行RUNでは、スコア、投稿量・応答時間、JSON経路のCPUと割当て量、
WAL同期回数・時間を比較する。CPU割合だけを得点の改善幅として扱わない。
