# WAL同期のバッチ化

この固定収集待ちは後続の改善で削除した。現行仕様は
[JSON応答の再利用とWAL同期待ちの削減](json-response-wal.md)を参照する。

2026-10-02。同期開始前の短い収集待ちにより、1回のfdatasyncへ含めるイベントを増やす。
対象は3号機のGoアプリ。基準RUNは20261002-013620、482610点、PASS。

## 根拠と条件

実負荷60秒内の59秒のサンプル差分で、67610イベント、41731同期、同期時間43.837秒。
平均1.62イベント/同期、1.05ms/同期。3号機のディスク稼働率は99.3%、I/O待ちは20.0%。
これは同期回数削減を試す根拠であり、装置の性能上限や得点改善幅の確定ではない。

未同期イベントが4件以上になった場合、または最古の未同期フレームの追記完了から
500µs経過した場合、同期workerが完全フレームをすべて取り出す。4件は開始条件であり
上限ではない。期限を過ぎていれば追加待ちを入れない。後続追記で期限を延長しない。
追記とfdatasyncは引き続き並行する。タイマーはworker内で再利用し、空なら停止する。
500µsは収集期限であり、OSの起床遅れを含む実際の待ち時間の保証ではない。

## 永続化と終了

同期対象の末尾境界を捕捉してからfdatasyncし、成功後にWAL順でメモリへ公開して
要求の完了を通知する。同期中の後続追記を、その同期で成功扱いしない。
配信ごとのgate、受付後のキャンセル処理、失敗時の応答、容量上限を維持する。
追記workerの終了通知で収集待ちを解除し、残ったフレームを処理して同期workerを終了する。
ISUPWAL3の形式と復旧処理は維持し、DB再作成や初期化を必要としない。

## 計測と評価

既存の/debug/sql-poolsとsnapshot collectorへ次の累積値を追加する。

- wal_group_waits_total: 収集待ちに入ったグループの数。通知回数ではない。
- wal_group_wait_ns_total: 収集待ち開始から対象を取り出すまでの実時間。起床遅れを含む。
- wal_single_record_syncs_total: 1イベントだけの同期試行回数。

既存のイベント数・同期数・同期時間と併せ、同じRUN・同じ負荷窓内のカウンタ差分で比較する。
スコア、イベント/秒、コメント・リアクション・モデレーションの応答時間を優先する。
同期数が減っても処理量が落ちた場合は改善と判定しない。基準の投稿平均はコメント3.571ms、
リアクション2.814ms。p99はコメント10ms、リアクション8ms。
低負荷時の追加待ち、タイマーの起床遅れ、同期後の次の律速は未確定。

## 確認

- task check-fast-paths: race付きテスト、同期境界・キャンセル・失敗・追記並行化。
- 追加テスト: 固定期限、件数到達、上限を設けない取り出し、タイマーと終了通知による排出。
- task check-app-improvements: 一時DBで全イベントの再生、NG判定、削除、統計の一致。
- task deploy-app-dry: 配布先と再起動対象が3号機だけであること。

ベンチはユーザーが実行する。

## 実施結果

- task check-fast-pathsが成功。追加テストを含むrace検証とsnapshot collector契約を確認した。
- task check-app-improvementsが成功。1号機の一時DBで、全イベント・同時更新・再起動・
  不完全末尾の復元と破損拒否を確認した。ログは.task/wal-group-commit-mysql.log。
- 全ホストのLinux/amd64、collectorとプロファイルの停止を確認し、task buildで
  ローカルクロスコンパイルした。
- task deploy-appで3号機だけへ配布・再起動した。既存WAL世代
  973608ac-92ee-4d50-b4b4-3c943ab38339、durable_seq=published_seq=68689、
  WALサイズ12305783 bytes、rows=80054を維持した。
- 公開APIで9イベントを保存し、再度task deploy-appで3号機を再起動した後、両入口で
  ログイン・8認証APIと投稿・NG登録・削除後の通報内容・視聴・統計・課金の一致を確認した。
  WAL世代、durable_seq=published_seq=68698、WALサイズ・rowsを再起動前後で維持し、
  pending_bytes=0、failed=falseだった。稼働バイナリもローカルのSHA256と一致した。
- 既存の書込みsmokeは初回入口で成功し、2番目の入口ではNG登録済みのため、
  未モデレーションの対象配信がなく終了した。初回の保存結果を使う読取りsmokeは
  再起動後に両入口で成功した。smoke自体のコードは変更していない。
- 少数の逐次要求では9イベント/9同期で、収集待ち9回、実時間合計9570975ns、
  平均1.063msだった。500µsの収集期限に対して起床等の遅れがあることを確認した。
  このsmokeでは同期回数削減の効果を評価できず、負荷時の得点と応答時間は未測定。

反映ログは.task/wal-group-commit-deploy.log、再起動後の公開API確認は
.task/wal-group-commit-read.log、WAL状態は.task/wal-group-commit-{before,after-deploy,
after-write,after-restart}.logに保存した。ベンチマーカーは実行していない。
